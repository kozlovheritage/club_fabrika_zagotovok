# Закрытый контроль оплат и писем

## Статус и ограничения

Этот пакет подготовлен и проверен, но не опубликован. Он включает ранее подготовленный серверный поток CloudPayments, **не переключая** действующую оплату: `CHECKOUT_PROVIDER=prodamus` остаётся значением по умолчанию. Изменения сайта продаж сюда не входят. Имена, фотографии, статьи и материалы текущего GitHub main не заменяются.

По умолчанию `CLUB_ADMIN_ENABLED=false`, `CLOUDPAYMENTS_ENABLED=false`. Не публиковать ветку в GitHub без учёта автоматического ONREZA Preview и общей рабочей базы. Изолированная проверка не должна использовать её DATABASE_URL или реальные ключи.

## Права и профиль владельца

- Админ-права привязаны к **точной внутренней записи пользователя**, а не к совпавшему login email. Другая покупка с тем же email прав не получает.
- Имя и роль изменяются отдельно от запуска сервера, транзакцией `provision-owner.mjs`. Ни email, ни пароль, ни тариф не обновляются.
- Значения владельца задаются приватно из его подтверждённого запроса, не в коде, URL, аргументах команд или публичных тестах.
- При отсутствии пользователя, нескольких совпадениях, неактивном аккаунте, несовпадении прежнего имени либо наличии другого администратора операция прерывается без изменений.
- Скрипт проверяет `CLUB_ADMIN_PROVISION_CONFIRMED=true` и совпадение приватного `CLUB_ADMIN_PROVISION_TARGET_URL` с `PUBLIC_URL`. Это дополнительный предохранитель, **не замена** проверки назначения DATABASE_URL.
- `CLUB_ADMIN_TARGET_EMAIL`, `CLUB_ADMIN_EXPECTED_NAME`, `CLUB_ADMIN_DISPLAY_NAME` используются только при однократном запуске скрипта. После успешного выполнения убрать их из операторского окружения.
- Отзыв прав: приватно отключить строку `club_admin_accounts.enabled`. Проверка на каждом запросе действует и для уже открытого кабинета.
- Используется текущая парольная авторизация клуба; двухфакторная проверка в этот пакет не входит. Владелец должен использовать уникальный пароль и защищённую почту.

После назначения роли в «Мой профиль» появляется «Оплаты и письма». Все страницы, CSS/JS и API `/admin` / `/api/admin` проверяют серверную сессию и роль. Записи заказов не помещаются в публичный HTML. Мутации требуют привязанный к сессии CSRF-токен, JSON и точный Origin платформы; источник сайта продаж не допускается.

## Доставка

- Сохраняются только ID сообщения NotiSend, получатель, перечислимый статус, безопасный код ошибки и времена. Полный ответ провайдера (с текстом и паролем) не хранится и не логируется.
- Официальный `GET https://api.notisend.ru/v1/email/messages/:id` проверяется сервером маленькими порциями с блокировкой задания. Публичный неподписанный webhook статусов не вводится.
- `queued` означает очередь NotiSend, `sent` — отправку без окончательного подтверждения, `delivered` — принятие сервером получателя, **не доказательство попадания во входящие или прочтения**.
- `skipped`, `soft_bounced`, `hard_bounced`, блокированная отправка, неподдерживаемый провайдер или неизвестный ID требуют внимания. Очередь отправки старше 10 минут, `queued` старше 30 минут и `sent` старше двух часов также выделяются.
- Кратковременный сбой отправки: повтор с увеличением задержки, максимум восемь подряд, затем ручная проверка. Bounces не запускают бесконечную повторную рассылку.
- Статусы Resend в этом пакете автоматически не проверяются. Для полноценного контроля необходим `AUTH_EMAIL_PROVIDER=notisend` и корректно настроенный отправитель.

Источник API-контракта: официальная страница `https://notisend.ru/dev/email/api/`, встраиваемый ею документ `https://doc.msndr.net/api.notisend.ru/email.html` (проверен 2026-10-13). Методы `POST /email/messages`, `GET /email/messages/:id`. API получения сообщения не обещает полный SMTP-трейс или причину антиспам-решения; панель не выдумывает их.

## Повтор и предупреждения

- Кнопка ставит в существующую очередь прежний доступ. Она не создаёт платёж, новый аккаунт, новый пароль или новое право доступа.
- Расширенный пароль восстанавливается для того же заказа и проверяется по текущему хэшу до постановки и перед отправкой. Сменённый пароль/неактивный доступ требуют проверки, а не отправки устаревших данных.
- Исправленный login email берётся из существующего аккаунта. В панели различаются email оплаты и актуальный адрес письма, в истории виден фактический получатель.
- Необходимы причина и подтверждение. Для уже доставленного, пропущенного или hard-bounced письма требуется запрос клиента. Переподписка, снятие suppression или обход ограничений провайдера не выполняются.
- Минимальный интервал 10 минут; не более 30 ручных повторов в час на администратора. Параллельный повтор или устаревшая форма получают отказ.
- В аудит пишутся время, администратор, заказ и действие — без пароля, тела письма, данных карты или сырых ошибок провайдера.
- При настроенном приватном `CLUB_ADMIN_ALERT_EMAIL` владелец получает общее предупреждение со ссылкой на закрытую панель и количеством проблем. Повторное предупреждение не чаще шести часов; после устранения — одно сообщение восстановления. Ошибка самого alert API повторяется не чаще часа.
- Если почтовый провайдер не работает, предупреждение через него тоже может не прийти. Панель сохраняет проблемы независимо от почты. Независимый мониторинг запуска/доступности — отдельная существующая задача, не доказан этим пакетом.
- При таймауте между принятием API и записью результата возможна повторная отправка: не обещаем exactly-once без документированной идемпотентности у почтового провайдера.

## Порядок выпуска

1. Получить отдельное разрешение на выпуск админ-раздела и подготовленного серверного кода **без переключения Prodamus**. Показать фактический diff и сверить свежий main; при изменении main не затирать параллельные правки.
2. Сделать и проверить резервную копию схемы/данных; помнить, что ONREZA Preview может использовать ту же базу, что Production. Автоматический Preview не использовать как безопасную песочницу.
3. Прогнать пакет с синтетическим окружением в отдельном локальном PostgreSQL: `bash test-admin-postgres.sh`. Требуются Node >=20, зависимости существующего package.json, PostgreSQL CLI, Playwright и Chromium. Скрипт не наследует DATABASE_URL/секреты рабочего процесса.
4. Подтвердить настройки почтового отправителя и приватный email предупреждений. Развернуть с флагами оплаты без изменений. Включение админ-раздела запускает только добавочные миграции `ADMIN_SCHEMA`; его включение не требует активации CloudPayments.
5. Однократно выполнить `node provision-owner.mjs` в проверенном и разрешённом окружении. Перед запуском сверить точный аккаунт владельца и ожидаемое прежнее имя. Скрипт выводит лишь общий успех/ошибку, не персональные данные.
6. Проверить владельцем вход, нужное имя, наличие панели; обычной учёткой — отказ к странице и API. Пока CloudPayments отключён, панель честно сообщает, что его заказов ещё нет. История Prodamus не импортирована и не выдается за проверенные письма NotiSend.
7. CloudPayments и настоящие письма проверять/включать только отдельным согласованным этапом после подготовки магазина, кассы и действующих документов обработки персональных данных.
